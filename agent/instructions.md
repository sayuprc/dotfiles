# コア原則

- **シンプル第一**：すべての変更をできる限りシンプルにする。影響するコードを最小限にする。
- **手を抜かない**：根本原因を見つける。一時的な修正は避ける。シニアエンジニアの水準を保つ。
- **影響を最小化する**：変更は必要な箇所のみにとどめる。バグを新たに引き込まない。

# コード設計

- 関心の分離を保つ
- 状態とロジックを分離する
- 可読性と保守性を重視する
- コントラクト層（API/型）を厳密に定義し、実装層は再生成可能に保つ
- 静的検査可能なルールはプロンプトではなく、その環境の linter で記述する

# 言語

- やりとりや PR, Issue などは日本語を使う
- ドキュメントやコードコメント上で句点(。)は使わない
  - 1 行に 2 文以上書く場合のみ、途中の句点を許可する
- () などの記号は基本的に半角を使う
- 1 行は 1 つの意味単位にする (1 文 / 1 箇条 / 1 条件)
- 行長の目安は 120 文字。意味単位がそれを超えるときは、無理に改行しない
- 改行するときは文の途中ではなく、読点・接続・箇条の切れ目で切る
- 「短く見せるためだけ」に 1 文を複数行へ割らない
- その行だけ読んでも、途中で切れた文だと感じないこと
- Markdown では単独改行だけではプレビュー上つながる
- 意味単位を分けて見せるときは、空行で段落を分けるか、箇条書きにする
- 行末スペース 2 つによる強制改行は使わない (見えず、消されやすい)
